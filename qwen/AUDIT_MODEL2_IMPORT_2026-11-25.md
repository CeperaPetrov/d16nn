## Что вычисляет импортёр

1. `_validate_qwen_state_dict` сверяет формы и обязательные параметры до выделения памяти под модель. `D16QwenImportConfig` выделяет один комплексный канал на каждую исходную скрытую координату. В тестируемом режиме `gate` переносятся обе входные проекции MLP и выходная проекция.
2. При `second_coord_mode="zero"` второй компонент равен нулю. Роли найденных четвёрок задают, куда записать **исходный** вес. Из 494 032 768 значений 14 652 288 записаны по мнимой оси. Раскладка распространяется на строки up/gate и соответствующие столбцы down.
3. При `second_coord_mode="d16_sat_rope_gate"` исходный вес записывается в Re. Для большинства матриц Im вычисляется детерминированной формулой с насыщением и RMS. Для Q/K используются партнёры по половинам головы, для up/gate — взаимные проекции, для ряда других матриц — соседние столбцы. Коэффициенты нормализации переносятся по вещественной оси. Детектор четвёрок запускается, но его маска ролей не назначает координаты в этом режиме. В отчёте `total_im_weights=0` означает «ноль исходных весов размещены по оси Im». Среди 3 188 проверенных позиций 2 896 имели вычисленную ненулевую Im.
4. Роли в режиме `zero` частично эвристические. Если все три партнёра получили диагональные операции, код принудительно помечает первого и третьего партнёров как Im. Поэтому метка роли сама по себе не доказывает физический смысл компоненты исходного нейрона.

## Где меняется функция модели

**Вентиль MLP.** Для вещественных входов оригинал вычисляет `L * SiLU(E)`. При `mlp_activation="gate"` model2 использует `z * g.sigmoid()`, где метод D16 радиально масштабирует число приблизительно как `g / (1 + |g|)`. При `L=1, E=-1` вычисленные отклики равны −0,268941 и −0,500000 соответственно. Эти значения различаются уже на вещественной оси.

**Внимание и выходной словарь.** Метод `wedge_softmax` определяет силу сигнала через его модуль. Например, для вещественных оценок `[-2, +2]` обычный softmax даёт `[0.017986, 0.982014]`, у model2 получается `[0.5, 0.5]`. Правило действует и при отключённом пороге.

**RoPE.** Режим `half_head` повторяет частоты Qwen для двух половин головы. У model2 каждый комплексный канал поворачивается в своей плоскости. У исходной Qwen поворот смешивает соответствующие вещественные компоненты двух половин. Проверка с одной парой, `q=(1,0)`, `k=(0,1)`, позициями 1 и 0, даёт до масштабирования `sin(1)=0,841471` у оригинала и `0+0i` у model2 для вещественного вложения. Равенство частот само по себе не обеспечивает равенства attention scores.

Комплексное матричное умножение в этом пути выполняет `unpack()`, четыре вещественных матричных произведения и `pack()`. Это реализация комплексной матричной операции с переходом к декартовым координатам внутри метода.

## Воспроизведённые дефекты импорта и хранения

- **[P1] После успешного сохранения загрузчик может вернуть старые веса.** В один каталог сохранены модель с `norm.gain.x=1` в safetensors и отчёт, затем обновлённая модель с `norm.gain.x=3` в PT без отчёта. `load_d16_checkpoint` вернул **1 и прежний отчёт**. Старый safetensors имеет приоритет перед новым PT, а необязательный отчёт подхватывается по наличию файла. Исправление — связывать актуальные файлы весов и отчёта с конкретной версией сохранения, например атомарно обновляемым манифестом. [Сохранение](src/d16_qwen_importer.py#L1141) · [Загрузка](src/d16_qwen_importer.py#L1223)
- **[P2] Теряется пользовательское основание RoPE во вложенном формате конфигурации.** Создана небольшая HF Qwen2 с `rope_parameters.rope_theta=17333`. Импорт из объекта модели и из каталога после `save_pretrained` в обоих случаях дал `model2.config.rope_theta=1000000`. Исправление — читать оба формата, проверять поддерживаемый тип RoPE и отдельно тестировать перенос нестандартного основания. В испытанном официальном 0.5B snapshot значение указано на верхнем уровне и равно 1 000 000. [Чтение конфигурации](src/d16_qwen_importer.py#L63)

## Как повторить сравнение

Использованы Python из `torch_env`, CPU, четыре потока, исходные веса checkpoint bfloat16 с преобразованием в float32 для обоих прямых проходов. Эталон загружен с `attn_implementation="eager"`. Для model2 заданы `mlp_activation="gate"`, `indiff_eps=0.0`, `min_orbit_score=0.25`, `dtype=torch.float32` и по очереди оба значения `second_coord_mode`. Четыре независимых фрагмента обрезаны до 12 токенов каждый. Токенизатор исходной модели, без специальных токенов. Ниже приведены точные входы.

```python
ids = torch.tensor([
    [785, 6722, 315, 9625, 374, 12095, 13, 576, 6722, 315, 15344, 374],
    [32, 21495, 702, 2326, 11067, 323, 279, 2629, 315, 1181, 14791, 25941],
    [28253, 93377, 518, 7168, 12348, 61347, 323, 88955, 518, 825, 7739, 12348],
    [16206, 86778, 127912, 7599, 8959, 26909, 36305, 6709, 3780, 124763, 24725, 125879],
])
```

В `eval()` и `torch.inference_mode()` для HF берутся `hf(ids).logits[:, :-1].float()`, для model2 — `model(encode_token_ids(ids)).logits[:, :-1].wedge_strength(eps=0.0)`. Далее к обеим матрицам оценок применяется `log_softmax(dim=-1)`. NLL усредняется по целевым `ids[:, 1:]`, top-1 сравнивается для одинаковых префиксов. При температуре 1 и выключенном пороге это соответствует используемому model2 правилу выбора токенов. Веса сохранённых ранее D16-моделей для этой таблицы не использовались.

Сохранённый в [блокноте](ipynb/d16_model2.ipynb) результат `13/13` измерен после обучения на одной последовательности. Четыре токена генерации заданы входным префиксом, девять модель должна предсказать. Это отдельный эксперимент с другими условиями.
